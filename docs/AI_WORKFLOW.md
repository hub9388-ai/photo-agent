# PhotoAI AI 工作流工程化说明

本文档用于说明 PhotoAI 摄影多 Agent 项目是如何借助 AI 工具完成复杂系统拆解、后端改造、前端搭建和 Demo 稳定性设计的。它不是简单记录“用了哪些工具”，而是说明我如何把 AI 当成工程协作工具使用，并控制它的边界。

## 1. 为什么选择摄影多 Agent 场景

我选择摄影场景，是因为它天然不是一次性问答，而是一个完整工作流：

- 拍摄前：地点、时间、路线、机位、器材、天气和风格目标。
- 拍摄后：曝光、色彩、构图、对焦、噪点、后期方向。
- 批量素材：筛片、分档、去重、归档、送去后期或学习复盘。
- 学习成长：从作品点评沉淀练习任务，再通过练习照片复盘。
- 历史沉淀：任务、事件、结果、素材和练习记录都需要可恢复。

所以我没有把它做成普通聊天机器人，而是做成“摄影多 Agent 工作台”。这能体现 Agent 协同、结构化输出、任务编排和前后端产品化能力。

## 2. AI 参与方式

AI 在项目中主要承担四类角色：

| 角色 | 使用方式 | 人工控制点 |
|---|---|---|
| 架构顾问 | 帮助盘点旧代码、识别 API 化风险、拆阶段 | 是否移动旧代码、MVP 边界、阶段验收由我决定 |
| 编码助手 | 生成 wrapper、API client、组件、类型、错误态 | 每次限定文件范围，跑测试验证，不接受一次性大重写 |
| 产品体验顾问 | 辅助设计页面信息结构、状态流、fallback 文案 | 页面是否符合摄影用户工作流由我判断 |
| 文档助手 | 整理项目说明、Prompt 模板、Demo 脚本 | 真实完成度、技术栈和取舍必须按项目事实校正 |

## 3. 阶段拆解

项目没有采用“一次性生成完整应用”的方式，而是拆成可验证阶段。

### 阶段 0：最小代码盘点与回归基线

目标是先确认旧系统能跑：

- 确认旧代码真实路径为 `agent_code/`。
- 确认 14 个 Python 文件可导入。
- 记录 Post / Coach / Plan / Asset 的真实入口函数。
- 记录 import 风险，例如旧文件内部裸导入。
- 建立最小回归测试，不强依赖真实模型 API。

人工判断：不移动旧文件、不为了目录漂亮破坏旧 import。

### 阶段 1-2：FastAPI 骨架与 API 契约

目标是先建立稳定后端外壳：

- 新增 `backend/app`。
- 通过 `ensure_agent_code_on_path()` 兼容旧裸导入。
- 定义 Media、Job、Event、Result、Handoff、AgentRequest。
- 定义 Response Models，区分内部模型和对外契约。

人工判断：AgentRequest 不做 legacy 参数搬运工；`client/system/messages/media_items` 仍由 Service 内部组装。

### 阶段 3-4：媒体上传与 Job/Event/Result

目标是让后端具备 Web 产品的基本任务系统：

- `/api/media/upload` 保存原图、预览图、metadata。
- `POST /api/jobs` 创建任务。
- `GET /api/jobs/{job_id}/events` 用 SSE 推送事件。
- `GET /api/jobs/{job_id}/results` 恢复结果。
- 关键事件入库，`agent.delta` 高频文本不入库。

人工判断：MVP 先用 SQLite + 本地文件，不引入 Redis/Celery/PostgreSQL。

### 阶段 5：Post + Coach 并行 MVP

目标是跑通第一个真实闭环：

```text
上传照片
→ 创建 photo_review job
→ PostAgent + CoachAgent 并行运行
→ SSE 展示状态
→ ResultStore 保存结果
→ 历史页恢复
```

人工判断：一个 Agent 失败不导致整个任务失败，设计 `partial_completed`。

### 阶段 6-8.5：稳定化、素材、规划、Skills 后置

目标是把核心 MVP 扩展成更完整的摄影工作台：

- 阶段 6：错误码、重试、历史查询、API 文档。
- 阶段 7：素材管理后台化和 asset handoff。
- 阶段 8：PlanAgent 条件触发，不默认跟随照片上传运行。
- 阶段 8.5：Skills/MCP 后置，保留 legacy skills 能力但不污染主链路。

人工判断：PlanAgent 只能由显式规划需求触发；素材管理不抢单张照片分析主流程。

## 4. 前端从设计到真实链路

前端不是先写代码，而是先明确产品形态：

1. 使用 Pencil 设计工作台、分析、素材库、学习、规划、历史 6 个页面。
2. 拆路由和组件，先用 mock 数据还原页面结构。
3. 定义 TypeScript API 类型，和后端 Response Models 对齐。
4. 封装 API Client，避免组件里直接 fetch。
5. 先接最核心链路：工作台 → 分析页 → 历史页。
6. 再接学习页、规划页、素材页的轻量真实化。
7. 最后补错误态、fallback、local recovery 和 Demo 稳定性。

核心 UX 判断：

- 摄影应用以图片预览和任务结果为中心，不以聊天框为中心。
- 多 Agent 状态必须可视化。
- AI 输出必须拆成结构化卡片，避免长文本堆叠。
- 历史页是 Job Center，不是普通浏览记录。

## 5. 使用过的工具

| 工具 | 主要用途 |
|---|---|
| Claude Code / Codex | 仓库级代码理解、分阶段改造、测试修复、文档整理 |
| Cursor | 局部编辑、调试、类型和组件调整 |
| ChatGPT | 架构评估、阶段边界、项目说明和 Prompt 模板组织 |
| Pencil | 页面结构和视觉参考设计 |
| Google AI Studio / Gemini | 多模态 Prompt、摄影输出结构和模型行为对比 |

说明：工具名称不是重点，重点是我没有把问题直接丢给 AI，而是拆成有边界、有验收标准的小任务。

## 6. AI 工具边界

我对 AI 工具边界的理解：

- AI 很擅长生成初稿、补齐错误态、发现命名不一致、整理文档。
- AI 不擅长替我决定产品边界、业务优先级、真实完成度和提交策略。
- 旧代码迁移不能让 AI 一次性重写，否则风险不可控。
- Demo 数据必须显式标注，不能包装成真实生产能力。
- 每次改动后必须跑测试或手动 smoke，而不是相信生成结果。
- AI 输出不直接合并：先看计划，再看 diff，再跑测试，最后做手动 smoke。

本项目中由我明确控制的判断包括：

- 不公开源码，以网页链接、视频和文档验收。
- 不移动 `agent_code/`，先 wrapper 化。
- 不把 PlanAgent 放进默认照片上传主流程。
- 不把素材库轻量规则包装成完整 DAM。
- 不引入阶段 10 的生产级基础设施，优先完成可演示 Web MVP。

## 7. 真实纠偏例子

下面这些例子体现了我在 AI 协作中不是“接受生成结果”，而是持续用产品目标、工程约束和真实运行结果纠偏。

### 例子 1：分析页结果按钮不能停留在静态 UI

问题：分析页右侧已经有“导出报告、保存结果、拍摄规划、送去素材库”按钮，但它们一开始只是视觉展示，没有真实链路。

纠偏：

- “导出报告”改为生成 Markdown 报告，包含任务 ID、媒体信息、Post/Coach 结果和最近事件。
- “保存结果”明确利用后端 Job/Result 持久化，同时在前端记录最近保存项。
- “拍摄规划”不只是跳转页面，而是把当前照片的后期风格方向、学习反馈和来源任务写入规划草稿。
- “送去素材库”复用素材页的 `mediaToAssetItem()` 映射，写入素材库缓存，避免单独造一套字段。

人工判断：按钮必须承接用户分析后的下一步工作流，否则页面虽然好看，但不算产品闭环。

### 例子 2：规划页必须尊重用户硬约束

问题：PlanAgent 早期会忽略“从上午 9 点到下午 5 点”这类明确时间要求，或者只生成两个景点，缺少午饭和休息节点。

纠偏：

- 把“其他要求”和“迭代优化”作为硬约束传入 job context。
- 前端增加时间范围解析、午饭/晚饭节点识别、详细路线需求识别。
- 结果渲染时对泛化机位进行兜底，避免出现“推荐机位 1”这种不可执行内容。

人工判断：拍摄规划不是景点清单，而是可执行行程表；用户写在“其他要求”里的内容优先级不应低于表单字段。

### 例子 3：素材页轻量规则不能冒充完整 AssetAgent

问题：早期素材页用轻量规则给 A/B/C 分档和重复判断，容易被误解为完整图像理解能力。

纠偏：

- 文档和页面都明确“轻量规则 / 示例数据 / AssetAgent 评分”的边界。
- 后续接入 `/api/agents/asset/score`，让素材页具备更真实的视觉质量评分。
- 仍然保留“不是完整 DAM，不做生产级相似度去重”的说明。

人工判断：Demo 可以轻量化，但必须诚实标注完成度，不能把不稳定或半真实能力包装成生产能力。

### 例子 4：公网演示不能只按本地开发体验设计

问题：本地可以上传和 SSE 流式展示，但通过 Cloudflare quick tunnel 访问时，大图上传慢，SSE 可能出现 `stream canceled`。

纠偏：

- Demo 视频优先使用压缩 JPG，不使用 RAW 或超大图。
- 文档中说明公网 quick tunnel 只适合临时演示，不等同生产部署。
- 前端保留历史恢复、结果查询、Demo fallback，避免 SSE 中断导致页面不可演示。

人工判断：AI Demo 不能默认网络、模型和隧道都稳定；必须提前准备录屏和 fallback。

## 8. Demo 稳定性策略

AI Demo 的风险主要来自模型、provider、网络和大文件上传。因此我设计了：

- 分析页：Post/Coach 独立失败，支持 `partial_completed`。
- 历史页：结果从 Job/Result 恢复，刷新后不丢。
- 素材页：多图上传支持部分成功；handoff 失败 fallback 到 `/api/jobs`。
- 学习页：无练习任务时有空状态；Coach 失败可展示示例复盘。
- 规划页：天气/地点 provider 不可用时降级为通用规划建议。
- 公网演示：优先用压缩 JPG，避免 RAW/大图导致 Cloudflare quick tunnel 上传过慢。

## 9. 项目复盘

这次项目的核心价值不只是“写了一个网页”，而是把一个 CLI-first 多 Agent 原型逐步改造成：

```text
Web 前端
→ API 契约
→ Job/Event/Result
→ SSE 实时状态
→ 多 Agent Service wrapper
→ Legacy Agent 能力复用
→ 历史恢复与跨 Agent 流转
```

这条路径体现的是复杂系统拆解、渐进式重构、AI 工具协作和产品边界控制。
