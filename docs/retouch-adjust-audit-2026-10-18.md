## 阴影方向的代码核查

`pixels._tone` 使用：

```python
unit = value / 255
value += shadows * (1 - unit) * 64
value += highlights * unit * 64
```

在其他参数相同时，正的 shadows 提升像素值，且暗部提升更多。本地调用实际函数的合成像素检查：

| 输入灰度 | highlights=-0.35, shadows=0 | highlights=-0.35, shadows=+0.12 |
| ---: | ---: | ---: |
| 32 | 29 | 35 |
| 64 | 58 | 64 |
| 128 | 116 | 120 |
| 224 | 204 | 205 |

这是隔离验证阴影参数方向，不能冒充整张照片的像素测量。整张结果仍可因亮度、高光、饱和度等共同作用而变暗，并不否定阴影本身执行反向。

## 其他发现与限制

1. 用户提交的 goal 确实包含矛盾文字：“阴影建议降低 -10”，后面却写“含义：提亮暗部”。规划回复明确称将阴影符号反转。该错误说明可能影响规划，但未做移除说明后的对照实验，不能宣称已证明完整因果链。
2. Post 原始 adjustments 还包含整体略降曝光、轻微冷调、绿色 HSL 降饱和/亮度和暗角要求。xmp_params 未包含所有这些内容；前端参数区优先展示 XMP，用户此次复制的 goal 只有上表8项。因此此次没有完整传递原始建议。temperature=0、vignette=0 也证明这些工具项没有执行，绿色 HSL 本身不在现有工具能力中。
3. 该会话截至查询时只有一次 adjust_image。之后有 scale_layer、rotate_layer、reorder_layer 操作；这些不是重复调色。当前会话修订号已到4，不能把当前会话状态当作调色刚完成时的状态。
4. 输入使用的是 base 图层；本次为整个图层调色，不是只针对猫咪或背景绿植的局部调整。
