# 面试准备：用这一例讲清楚 Agent 评测

## AI 产品经理视角（约一分钟）

我在摄影多 Agent 项目中发现，用户看到“调色完成”，并不意味着照片按建议调整。一个真实案例里，Post 要求阴影降低，修图助手却把阴影参数传成正数，同时擅自用亮度和锐化代替工具不支持的能力。我把技术执行成功与用户意图满足分开，保存原始建议、真实工具调用和失败证据，并建立第一条可重复的规则评测。当前完成了历史案例重放和判定器检查，后续用相同标准验证转换逻辑修复；还没有把单例包装成系统成功率。

## AI 应用开发视角（约一分钟）

我先对齐 Post 结果、规划步骤和数据库中的 ToolRun，确认错误发生在建议到工具计划的转换阶段，而不是参数校验或执行异常。合法的 shadows=+0.12 通过了范围检查，但违背源建议的负向要求。为此建立独立 case 与 trace，用无模型依赖的规则判断调用次数、参数方向、范围及不支持项是否被替代。真实历史工具状态为 succeeded，语义约定却有5项失败。人工正向样例只验证判定器，不作为 Agent 修复成果。

## 常见追问

**这和普通单元测试有什么区别？**

被评测对象是一次 Agent 规划/执行记录，检查的是业务语义；`test_evaluate.py` 则是判定器的单元测试。两者不能混为一谈。本阶段是离线重放，尚非自动重跑 Agent 的端到端评测。

**为什么不用模型来当裁判？**

方向是否反了、是否调用不支持项，可以用可解释规则检查，费用与波动更低。审美、解释质量适合后续人工评分或审慎引入模型裁判。

**怎么知道不是数据库记录与执行不一致？**

对齐了规划表和工具表的参数，并检查执行函数直接把非零参数传给像素函数。历史审计还用合成灰度像素验证正 shadows 提亮暗部。它是可追溯证据，尚不等于完整分布式追踪或逐像素执行证明。

**参数都在 -1～1，为什么仍然失败？**

范围合法只表示接口能接受，无法保证方向符合用户需求。需要语义约定，例如源建议降低阴影时不能执行正向提升。

**负值就一定代表修图正确吗？**

不一定。这里只检查方向，幅度可能仍不合适；还需图像样本校准和质量评测。Pillow 参数与 Lightroom 参数不能直接等同。

**只有一条样本，能说明系统提升了吗？**

不能。它是回归起点，覆盖一个已知失败模式。修复后须收集真实新记录，并逐步扩展不同图片、意图、冲突和异常输入。当前不能声称准确率提升。

**如何连接 EvalScope？**

先复用样本与规则，再按使用版本写 Agent 输出采集和自定义评测适配。本目录尚未接入，不声称使用了 EvalScope 完成评测。
